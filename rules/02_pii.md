# Регламент: Персональные данные (PII)

## Цель
Не допускать публикацию персональных, контактных и платежных данных, которые позволяют идентифицировать человека, связаться с ним вне платформы или использовать данные во вред.

## Технические зависимости и контракт
- `pii_patterns`: набор regex/NER-шаблонов с типом сущности `phone|email|address|bank_card|bank_account|passport|messenger|social_profile`.
- `pii_ner_entities`: результат NER-модели, массив `{entity_type, value, confidence, start, end}`.
- `ocr_result`: массив блоков `{text, confidence}` для каждого изображения.
- `doc_image_score`: вероятность, что изображение содержит документ/карту/чек, число `0.0..1.0`.
- `financial_context_terms`: словарь терминов для банковских/платежных реквизитов.

Минимальный формат:
```json
{
  "pii_patterns": [{"type":"phone", "pattern":"..."}],
  "pii_ner_entities": [{"entity_type":"email", "value":"x@y.z", "confidence":0.94}],
  "financial_context_terms": ["номер карты", "cvv", "iban"]
}
```

## Термины и определения
- **PII**: данные, по которым можно идентифицировать человека напрямую или косвенно (ФИО+контакт, адрес, документы).
- **Финансовые реквизиты**: номера карт, счетов, CVV/CVC, банковские идентификаторы, платежные токены.
- **Частично замаскированные данные**: данные вида `****1234`, `+7***`, где нельзя восстановить полное значение без внешних источников.
- **Контакт для обхода платформы**: просьба писать в мессенджер/соцсеть/телефон для продолжения коммуникации вне площадки.

## Нормализация входа
- Хранить `raw_text` и `normalized_text`.
- Для `normalized_text`: lowercase, унификация пробелов, замена типовых маскировок (`(at)`, `[dot]`, `тчк`, `собака`) на канонический вид.
- Удалять визуальные разделители в номерах (`-`, `_`, пробелы), сохраняя возможность восстановления исходной формы для логов.
- OCR-текст обрабатывается теми же правилами нормализации.

## Алгоритм проверки
1. Проверить `raw_text` и `normalized_text` через `pii_patterns`.
2. Запустить NER и отфильтровать сущности с `confidence >= 0.75`.
3. Сопоставить паттерны и NER:
- совпали оба источника -> высокий confidence нарушения;
- сработал один источник -> средний confidence, возможен `REVIEW`.
4. Для изображений:
- если средний OCR confidence < `0.65`, пометить `LOW_OCR_CONFIDENCE` и отправить в `REVIEW`;
- если OCR confidence >= `0.65`, прогнать OCR-текст через тот же пайплайн PII;
- если `doc_image_score >= 0.80`, считать риск утечки документов/карт высоким.
5. Усилить риск, если найден CTA на внешний контакт (`пиши`, `звони`, `в тг`, `в ватсап`) рядом с PII.
6. Выставить итоговое решение по таблице и приоритетам.

## Таблица решений (детерминированная)
- `REJECT`:
- Есть `PII_FINANCIAL`.
- Или есть `PII_DOCUMENT_IMAGE` при `doc_image_score >= 0.80`.
- Или есть явный `PII_PHONE|PII_EMAIL|PII_ADDRESS` + призыв к контакту вне платформы.
- `REVIEW`:
- Обнаружен вероятный PII только одним источником (regex или NER), confidence пограничный.
- Или данные частично закрыты, но есть риск деанонимизации в контексте.
- Или `LOW_OCR_CONFIDENCE` при подозрении на PII в изображении.
- `APPROVE`:
- Нет reason-кодов PII.
- Либо присутствуют только безопасно замаскированные данные (`****1234`) без дополнительных идентификаторов.

## Приоритеты и мультиразметка
- Формат: `primary_reason_code` + `secondary_reason_codes[]`.
- Порядок приоритета:
1. `PII_FINANCIAL`
2. `PII_DOCUMENT_IMAGE`
3. `PII_PHONE`
4. `PII_EMAIL`
5. `PII_ADDRESS`
6. `LOW_OCR_CONFIDENCE`
- Если одновременно найдены телефон и email, `primary` выбирается по более точному совпадению (полный контакт > частичный).

## Reason codes
- `PII_PHONE`: опубликован телефон в явной или нормализуемой форме.
- `PII_EMAIL`: опубликован email, включая обфусцированные формы после нормализации.
- `PII_ADDRESS`: опубликован полный/достаточно точный адрес проживания или доставки конкретного лица.
- `PII_FINANCIAL`: публикация банковских/платежных реквизитов.
- `PII_DOCUMENT_IMAGE`: изображение документа, банковской карты, чека с чувствительными реквизитами.
- `LOW_OCR_CONFIDENCE`: технический код, OCR не дал надежного качества для автоматического решения.

## Примеры
- `REJECT`: "Переводите на карту 4276 12** **** 3456, пишите в тг @example".
- `REJECT`: фото паспорта/карты с читаемыми реквизитами.
- `REVIEW`: "мой номер +7 9** *** ** **" без других данных.
- `APPROVE`: "Оплата прошла, последние 4 цифры карты ****1234".

## Edge cases
- Упоминание публичных контактов компании (официальный саппорт) не считать PII физлица, если нет личной идентификации.
- Наборы цифр длиной 4-6 без контекста не классифицировать как финансовые реквизиты.
- Фразы вроде "пиши в тг" без конкретного контакта -> не `REJECT`, но могут усилить другие нарушения.
- Внутренние ID заказа/чека не считать PII, если по ним нельзя восстановить личность/платежные данные.

## Тестовая матрица
- T1: Полный телефон в тексте -> `REJECT`, `PII_PHONE`.
- T2: Email в obfuscation (`name(at)mail(dot)ru`) -> `REJECT`, `PII_EMAIL`.
- T3: Номер карты + CTA -> `REJECT`, `PII_FINANCIAL`.
- T4: Фото документа (doc_image_score >= 0.80) -> `REJECT`, `PII_DOCUMENT_IMAGE`.
- T5: Частично скрытый номер без контекста -> `REVIEW`.
- T6: `****1234` без других идентификаторов -> `APPROVE`.
- T7: OCR confidence < 0.65 и вероятный документ -> `REVIEW`, `LOW_OCR_CONFIDENCE`.
- T8: Ложноположительный контроль: "заказ #123456" -> `APPROVE`.
